# Technical Enabler: Incremental sync + persistence + unassigned bucket

**ID:** EN4.2 · **Type:** Enabler · **Feature:** F4 · **Epic:** E1
**Labels:** `enabler` `priority-high` `backend`
**Estimate:** 5 pts
**Blocked by:** EN4.1, EN2.3

## Description
**Incremental** sync for a stored address: fetch only transfers since the saved
cursor, persist them, upsert holdings, and place newly discovered tokens into an
"unassigned" bucket for manual assignment (feeds S3.2). Transactions are stored
once and only appended to — never re-fetched. See `sync-and-persistence-design.md`.

## Implementation Tasks
- [ ] Store public address(es) per user (no keys) in `wallets`.
- [ ] Incremental fetch: transfers from `last_synced_block` (with ~20-block overlap for reorgs).
- [ ] Persist raw transfers → `wallet_transfers`, **idempotent** on `(wallet_id, tx_hash, log_index)`.
- [ ] Upsert holdings (source=ON_CHAIN, wallet_ref) from current balances.
- [ ] Unassigned bucket for tokens with no portfolio yet.
- [ ] Update `last_synced_block` / `last_synced_at` / `sync_status`.
- [ ] Graceful failure: keep last-known + surface error (no rollback of stored history).

## Acceptance Criteria
- [ ] First run backfills; later runs fetch only new blocks (no full re-scan).
- [ ] Re-running a sync never duplicates transfers (dedup verified).
- [ ] New tokens appear unassigned; holdings reflect current balances.

## Definition of Done
- [ ] Integration test (T4.1) green incl. cold-start, warm-delta, and failure paths.
